# Architectural Decisions — Pomona GradGuide

Cross-cutting decisions, in the lightweight ADR format (Nygard). One file, by
repository convention (`docs/AGENT_PROTOCOL.md` §3). Manager owns it. Workers
propose changes through their handoffs; only the manager records them here.

Lifecycle: proposed → accepted → deprecated | superseded by ADR-NNN.

---

## ADR-001 — No runtime server, no database, no accounts

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: project owner (brief §1, §4, §11), manager

### Context
The whole catalog is a few MB of JSON. Storing other students' course histories on a server takes custody of exactly the education records the College may not release, for no capability gain in P0.

### Decision
A static single-page app plus a nightly build job. Student data lives in `localStorage`, exported files and share-link fragments only. "Backend" means the ingestion pipeline (`packages/pipeline`), whose deliverables are files in `/data`.

### Alternatives considered
- **Thin API + Postgres** — pros: accounts, sync across devices; cons: FERPA-adjacent custody, ops, attack surface, consent forms. Why not: zero P0 capability needs it.
- **Serverless functions for data fetch** — pros: fresher data; cons: a runtime dependency on Hyperschedule/Coursedog availability, and the Hyperschedule maintainers ask not to be called from browsers at scale. Why not: nightly snapshots are fresh enough for registration planning.

### Consequences
- Positive: free hosting, no secrets anywhere in the repo, privacy argument is structural, reviewer can verify with the network tab.
- Negative: no cross-device sync; share links carry the plan; the template's HTTP-oriented tooling had to be reinterpreted (ADR-002).
- Risks: someone proposes a server "just for analytics" → rejected by `docs/PRODUCT.md` out-of-scope table.

## ADR-002 — `packages/shared` zod schemas are the authoritative contract; `openapi.yaml` is generated

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: manager (via `ecc:contract-first`)

### Context
The template assumes an HTTP API enforced by `scripts/contract-test.sh` probing `/api/health`. This project's boundaries are static JSON files and two pure functions. Hand-maintaining TS types, JSON Schema and OpenAPI separately guarantees drift.

### Decision
zod 4 schemas in `packages/shared` are the single artifact. Types are `z.infer`. `docs/openapi.yaml` is generated by `npm run contract:openapi` (zod's built-in `toJSONSchema`, registry mode) and CI fails when stale. `scripts/contract-test.sh` checks the yaml is current and validates every `/data` file against the schemas, exiting 2 (never 0) when artefacts do not exist yet. The pipeline validates at write time; the app validates at load time; the engine's `Result` is validated in tests.

### Alternatives considered
- **Hand-written openapi.yaml + generated types** (openapi-typescript) — pros: yaml is the familiar source; cons: no runtime validation without a second library, and the "API" is not HTTP. Why not: runtime validation of files and imports is the actual need.
- **Plain TS interfaces, no runtime schema** — pros: zero deps in shared; cons: a corrupt artefact or import is only caught by a crash. Why not: `unverifiable` and specific error states are core product promises.

### Consequences
- Positive: one source of truth; imports, artefacts and goldens all validated with the same code; contract drift is a CI failure.
- Negative: `shared` carries one runtime dependency (zod, ~15 KB gz in the app); the generated yaml is verbose (1,700 lines).
- Risks: someone edits `openapi.yaml` by hand → CI `--check` fails.

## ADR-003 — npm workspaces monorepo; template `frontend/`, `backend/`, `tests/` removed

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: manager

### Context
The brief specifies `packages/shared`, `packages/engine`, `packages/pipeline`, `apps/web`, `data/`. The template ships empty `frontend/`, `backend/`, `tests/` placeholders and `bootstrap.sh`/CI written for npm at the root.

### Decision
npm workspaces (`packages/*`, `apps/*`), source exports for libraries (`"exports": "./src/index.ts"`, no build step for `shared`/`engine`), shared `tsconfig.base.json`, root scripts proxy to workspaces. Tests live beside code. pnpm is not installed on the owner's machine and the template tooling is npm.

### Alternatives considered
- **Keep `frontend/` and `backend/`** — why not: the brief's layout encodes the dependency rule (`shared ← engine ← web`, `shared ← pipeline`) that the reviewer enforces.
- **pnpm workspaces** — pros: stricter hoisting; cons: not installed, template scripts assume npm. Why not: no benefit at three packages.

### Consequences
- Positive: one `npm install`, one CI job, `npm test` runs everything.
- Negative: source exports mean a consumer's bundler must handle `.ts` (Vite, vitest, tsx all do; a plain `node` run does not).

## ADR-004 — Frontend agent owns the engine; Opus on frontend, Sonnet on the pipeline

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: project owner (chose two workers over a third slice), manager

### Context
The engine is where correctness risk lives (silent wrong `satisfied`). The manager proposed a dedicated `agent/engine` slice; the owner preferred two workers.

### Decision
`packages/engine` and `apps/web` are both owned by `agent/frontend` (Opus, high effort), engine first (TASK-020). `packages/pipeline` is owned by `agent/backend` (Sonnet, high effort): mechanical, fully specified, covered by TDD on parsers and validators.

### Alternatives considered
- **Dedicated engine slice** — pros: parallel engine and UI, focused review; cons: a third session for the owner to run. Why not: owner's call.
- **Opus on both workers** — cons: cost; the pipeline's risk is covered by concrete validators and measured expectations. Why not: not where the risk is.

### Consequences
- Positive: engine and UI share one mind; no cross-branch engine/UI contract friction.
- Negative: UI screens 2–4 are serialised behind the engine; mitigated by the fixture-data fallback (ADR-009) and by TASK-021/022 not needing engine results beyond the empty state.
- Risks: pipeline needs judgment (Coursedog access changes) → manager may reassign backend to Opus at integration and record it here.

## ADR-005 — One page: no router, no tabs, no landing page

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: project owner (mid-planning instruction), manager

### Context
The brief lists five "screens". The owner does not want multiple pages or tabs.

### Decision
Every screen is a section or an inline disclosure on a single scrolling document (`docs/DESIGN_BRIEF.md` §Structural rule). No router dependency. Requirement rows expand in place; "What satisfies this?" lives inside the expanded row; export/import/share live in the footer.

### Alternatives considered
- **Tabs: Record / Audit / Share** — cons: the audit is only meaningful beside the record; a tab hides the cause from the effect. Why not: owner's call, and the document metaphor is stronger.

### Consequences
- Positive: the back button never lies; the whole audit is one screenshot; simpler state.
- Negative: the page is long on mobile; mitigated by section anchors and sticky summary line.
- Risks: a worker adds `react-router` "for later" → AC-P12 fails.

## ADR-006 — Share links carry the plan in the URL fragment; CSP `connect-src 'self'`

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: manager

### Context
Sharing a plan by URL is the distribution mechanism. A query string reaches the static host's access logs; a fragment never leaves the browser.

### Decision
`#plan=<base64url(deflate-raw(JSON))>`, decoded client-side with a preview and confirm, then `history.replaceState` clears it. The page ships a Content-Security-Policy meta with `connect-src 'self'` (plus `font-src 'self'`, self-hosted fonts) so any accidental external request fails visibly.

### Alternatives considered
- **Query string** — why not: logged by every host and proxy.
- **Short links via a service** — why not: a server (ADR-001).

### Consequences
- Positive: AC-P07 is verifiable with the network tab and structurally enforced by CSP.
- Negative: links are long (1–3 KB); a warning appears past 8,000 characters with the export file as fallback.

## ADR-007 — Contract deviations from the brief, driven by the catalog text

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: manager (after snapshotting the 2026-27 catalog pages)

### Context
The brief's types were designed before the GE rule text was read. The catalog's Degree Requirements page (hydration payload) states rules the brief did not model. Each change below is additive to the brief's shapes and lives in `packages/shared`.

### Decision
1. `Requirement.appliesWhen.studentType` — applicability as data. CI waived for transfers; PE is 2 for first-years and 1 for transfers (two requirements); post-matriculation credits differ for transfers. Waived results are `satisfied` with `waived: true`.
2. `Requirement.attestable` — any requirement can be self-certified (language paths 6–8, advisor-approved residency), rendered as a manual result. The `attested` rule kind remains for attestation-only requirements.
3. `Program.constraints[]` with `distinctDepartments` — "No two Breadth areas can be fulfilled with courses from the same department or program."
4. `attribute` rule gains `filter`, `unit: courses|credits`, `distinctTerms` — Breadth/overlays exclude abroad and external work except transfer students' pre-matriculation work; Area 6 sums partial credits; PE needs different semesters.
5. `credits` rule gains `includeExternal` and `caps` (advanced standing 2, external 16, cumulative 2 credits / 8 courses) — all from the Credit Requirements and Advanced Standing pages.
6. WI and SI use `denyOnly` on each other — "a single course cannot fulfill both."
7. Transfer coursework is a `CompletedCourse` with `provenance: transfer` (carrying `title`, `credits`, `attributes` when not in the catalog); `ExternalCredit` is exams only (`AP | IB | ALEVEL | SATII`).
8. External credit resolution is data: `subjects[]` + `rules[]` with `ExamMatch` and `effect: credit | attribute`. Credit (advanced standing: AP 4–5, IB **HL** 6–7, A-Level comparable) is separate from satisfying the language requirement (AP 4–5; IB Language B HL 6–7 **or Language A SL/HL 6–7**; SAT-II 650 non-Romanized; A-Level B except Chinese/Japanese). **The brief's "IB SL never qualifies" is correct for credit and wrong for Language A**; fixture F-03b is corrected accordingly.
9. `Result` gains `programId`, `viaAttestation`, `waived`, `confidence`, `violations`; `Section` gains `geCodes`; a `Manifest` artefact is added as the app's first load.
10. `Program.advisories[]` for rules not evaluated in P0 (final semester in residence, PE in year one, eight-semester limit).

### Alternatives considered
- **Implement `anyOf` in P0 for the language requirement** — why not: an unconfirmed attested child inside `anyOf` muddles the status semantics; `attestable` is simpler and more general.
- **Encode transfer PE/CI variants in engine code** — why not: violates "requirements are data" (brief §3 rule 2).

### Consequences
- Positive: the GE encoding is faithful to the catalog, with every rule beside its verbatim quote; majors will need these same constructs.
- Negative: more fields for the engine to implement; three requirements carry `confidence: draft` pending Registrar confirmation (`area-6` credits interpretation, `post-matriculation-credits-transfer`, `pomona-residency-credits` Claremont approval), and the A-Level credit cutoff is `unverified`.
- Risks: over-modelling; mitigated by only encoding rules the catalog states.

## ADR-008 — `catalog.json` contains every 5C course a Pomona student can count

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: manager

### Context
Coursedog's Pomona catalog has 2,811 PO courses. Pomona students satisfy Breadth with Claremont Colleges courses (a Scripps course tagged `1A2` counts), and the Registrar export lists 5,768 courses across 13 campus codes.

### Decision
`data/catalog.json` = Pomona courses from Coursedog (rich) + every non-PO course seen in Hyperschedule sections, built from section data with attributes from Pomona GE codes and `description: ""`. TASK-010 writes and preserves; TASK-012 merges. The Registrar CSV cross-checks both.

### Alternatives considered
- **PO-only catalog** — why not: students cannot enter or plan cross-campus courses, which is most of the scarce AD/SI supply.
- **Two catalogs** — why not: the engine and autocomplete want one list.

### Consequences
- Positive: autocomplete and candidates cover the real option set.
- Negative: non-PO entries lack descriptions; the file grows (~5 MB); the merge must never overwrite PO entries (tested).

## ADR-009 — Frontend develops against fixture data when the pipeline has not run; fixtures never ship

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: manager

### Context
Frontend and backend start in parallel; generated artefacts do not exist on `agent/frontend` until integration.

### Decision
The Vite dev plugin serves `/data/*` from the repo when `data/manifest.json` exists, otherwise from `apps/web/dev-fixtures/` with an unmissable "FIXTURE DATA" banner. `programs/*` and `external-credit-rules.json` (which exist) are always served from the repo. The production build throws if `data/manifest.json` is absent.

### Consequences
- Positive: TASK-021 to TASK-025 are demoable before TASK-013 lands; the engine fixture catalog is reused.
- Negative: a second small dataset to keep consistent; mitigated by a test that the fixture manifest validates and matches its files.

## ADR-010 — Requirements are data; the `Rule` union is defined in full, deferred kinds return `unverifiable`

**Date**: 2026-09-08 · **Status**: accepted · **Deciders**: project owner (brief §3, Approach A), manager

### Context
Majors and minors arrive in P1 (24 structured programs, 61 prose). Nothing in P0 may make that harder.

### Decision
GE is `Program #1` in `data/programs/`. There is no `checkGeneralEducation()`. The `Rule` union includes `allOf`, `anyOf`, `chooseN`, `fromSet`, `milestone`, `not` from day one; the P0 engine returns `unverifiable` with a note for them and never throws. AC-P11 proves a fake major is a JSON file only.

### Consequences
- Positive: no data migration when majors land; the data format is settled.
- Negative: `unverifiable` rows appear for any P1 fixture used early; that is the intended honest behaviour.
